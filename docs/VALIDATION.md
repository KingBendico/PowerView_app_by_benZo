**Validation — PowerView desktop, motion, appearance, shortcuts and saved controls, 17 September 2026**

The supplied local application is the baseline for this work. The corrected [evaluation](EVALUATION.md) distinguishes its existing features from remaining defects and future ideas.

- `npm run check`: all application, script and test JavaScript parses; referenced UI resources exist.
- `npm test`: 58 focused tests pass. Coverage includes finite requests, HTTP failures, malformed responses, cancellation, secondary-gateway rejection, per-home favorites, configuration recovery and legacy migration, partial group failures, Stop during movement, SSE chunking and subnet boundaries. Motion tests cover stale reads, late acknowledgments, event ordering, missing/invalid travel times, connection loss, simulated travel, intermediate Stop and per-home appearance persistence without motor commands. Curtain coverage includes both single-draw directions, paired geometry, existing-settings migration, demo mechanism changes and restoration, persistence across reconnection, pending-command handling and preservation of real hardware controls.
- `npm run smoke`: 41 native Electron checks pass on macOS arm64 with Electron 44.4.1. The test uses a temporary profile, demo data and a loopback HTTP/SSE fixture. It covers renderer isolation, percentage presets, numeric entry, stable drag targets during refresh, pointer cancellation, continuous demo travel, intermediate Stop, saved curtain appearance, horizontal curtain dragging, type 9 dual rails, keyboard controls, pinning, scene activation, navigation races, modal focus, dark theme, narrow/zoomed layouts, command search and Escape behavior, HTTP errors, acknowledgments, SSE updates and invalid IDs. Grips remain reachable at both endpoints, grabbing them preserves the position, and curtain grips select the correct panel. Dual-rail coverage verifies direct edge dragging, shared-grip direction, reversal without switching edges, refresh stability, ignored taps/sideways motion/unrelated pointers, all cancellation paths, crossing limits, independent numeric fields, bottom-edge shortcuts, keyboard focus and responsive grip spacing. Native mouse events verify actual grip/edge hit areas and pointer capture. Bedroom left switches to curtains, tests both single-draw directions and keyboard movement, and resets to the direct edge controls. The HTTP/SSE fixture also verifies travel-time animation, stale-read protection and settlement at the final reported position. No renderer errors were recorded. [Machine-readable results](native-smoke-results.json).

- Saved-control coverage verifies exact preset capture/recall, cross-room groups, input/home validation, timer confirmation/expiry/early restore, newer-command/scene/Stop cancellation, external position changes, connection loss, sleep cancellation, late-timer suppression, partial failures, preset shortcut invalidation and HTTP-success command-error responses. Native flows cover creating/recalling presets and groups, privacy countdown/restore/cancellation, and narrow editor layout. Light/dark room-grid captures verify readable room names.

The supplied LAN gateway’s Swagger document and read-only shade/automation endpoints were inspected; no real motor, schedule or network changes were made. See [API capabilities](API_CAPABILITIES.md). Physical movement has not been tested. Animation between gateway reports is an estimate based on an optional gateway travel time; it is not continuous position telemetry. Without that time, only reported positions advance the graphic. See [motion and appearance details](MOTION_AND_APPEARANCE.md). Broader type mappings, tilt/overlapped/top-down geometry, real discovery across networks, Swagger startup, device battery interpretation, sleep/resume, tray interactions on each OS, Windows/Linux builds and macOS distribution signing still need field/platform checks. The automated tests validate protocol handling and simulated behavior, not a real motor or every firmware version.

Routes and capability mappings were cross-checked against the [aio-powerview-api reference](https://github.com/sander76/aio-powerview-api/blob/master/aiopvapi/resources/shade.py), its [scene resource](https://github.com/sander76/aio-powerview-api/blob/master/aiopvapi/resources/scene.py) and [Home Assistant integration documentation](https://www.home-assistant.io/integrations/hunterdouglas_powerview/). The reference is guidance rather than proof of hardware compatibility. Renderer isolation follows [Electron's guidance](https://www.electronjs.org/docs/latest/tutorial/security).
